# 스케치캐치 앱 기획안 (RN 스터디용)

> 목표: React Native + Socket.io 기반의 실시간 멀티플레이어 스케치캐치.
> 학습 포인트: 실시간 통신, 캔버스(Skia) 드로잉, 소셜 인증, 친구 시스템, 미디어 변환(GIF).

---

## 1. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 클라이언트 | React Native (Expo + dev client) | 네이티브 모듈(react-native-skia, 카카오 SDK)을 위해 dev client 필수 |
| 상태 관리 | Zustand | Redux보다 보일러플레이트 적고, 게임 상태 관리에 충분 |
| 캔버스 | @shopify/react-native-skia | 60fps 보장, GPU 가속, stroke를 SkPath로 다룰 수 있음 |
| 서버 | Node.js + Socket.io | RN 학습 목적에 맞게 단순. 룸/네임스페이스 기본 제공 |
| DB | PostgreSQL (영구) + Redis (실시간) | 유저/친구는 PG, 게임 상태/획 데이터는 Redis |
| 배포 | Railway | PG/Redis 애드온 한 번에 가능, 비용 저렴 |
| 인증 | Kakao SDK + Apple Sign In + JWT | OAuth로 ID 발급 후 자체 JWT 발급 |
| 이미지 변환 | sharp + gifenc (서버 사이드) | 모바일 부담 최소화, 빠르고 메모리 효율적 |

## 2. 인증 / 프로필

### 소셜 로그인
- 카카오: `@react-native-seoul/kakao-login`
- 애플: `@invertase/react-native-apple-authentication` (iOS만, 안드로이드는 카카오 강제)
- 흐름: SDK로 ID 토큰 받기 → 서버에 전송 → 서버에서 검증 → 자체 JWT 발급 → 클라이언트 SecureStore에 저장

### 최초 가입 플로우
1. 소셜 로그인 성공
2. 닉네임 입력 (2~12자, 중복 검사)
3. 캐릭터 선택 (그리드 UI, 잠금 없이 전부 선택 가능)
4. 완료 → 메인 진입

### 마이페이지
- 닉네임 변경 (30일 1회 제한 권장)
- 캐릭터 변경 (제한 없음)
- 로그아웃 / 회원 탈퇴

## 3. 친구 시스템

- 검색: 닉네임 또는 6자리 친구코드(`#A1B2C3`) — 닉네임은 중복 가능하므로 친구코드 권장
- 친구 요청 → 알림 → 수락/거절
- 친구 목록: 온라인/오프라인/게임 중 상태 표시
- 데이터 모델: `users`, `friendships(userA, userB, status, createdAt)`

---

## 4. 게임 방 / 매칭

### 친구 초대 방
- 방 코드 6자리 자동 생성
- 방장이 인원수(3~12), 모드(1 or 2), 라운드 수, 타이머 설정
- 친구 초대 = 푸시 알림 + 방 코드 공유

### 랜덤 매칭
- 6/8/10명 옵션
- 매칭 큐: Redis Sorted Set (waitTime 기준)
- 30초 대기 후 인원 미달 시 안내 + 대기 연장 또는 취소

## 5. 대기실

- 참가자 액자 즉시 표시 (인원수만큼 빈 슬롯)
- 입장 시 해당 슬롯 채워짐
- '준비 완료' / '게임 시작' 버튼 캔버스 중앙
- 방장 나가면 다음 입장자가 자동 승계

## 7. 제시어

- 기본 모드: 서버에 카테고리별 단어 풀 → 라운드마다 랜덤 추출
- 직접 입력: 호스트가 모든 라운드의 제시어를 미리 입력 (모드 1) / 각 플레이어가 자신의 시작 제시어 입력 (모드 2)
- 길이 제한: 15자 (띄어쓰기 포함)
- 비속어 필터: 간단한 금칙어 리스트 (서버 검증)

## 8. 게임 모드

### 모드 1: 클래식 캐치마인드

- 라운드 = 출제자 1명 × 제한시간(10~60초, 기본 30초)
- 정답 처리:
  - 자동: 정확히 일치 (공백/대소문자 무시)
  - 수동: 출제자가 채팅에 뜬 답을 누르면 '정답 인정' 메뉴
- 점수 공식:
  ```
  맞힌 사람: max(100, 1000 - 경과초 × 30)
  출제자: 맞힌 사람 점수의 50% (최대 500)
  ```
- 시간 종료/전원 정답 → 다음 라운드

### 모드 2: 전언게임 (Gartic Phone)

- N명이면 N개의 시트(릴레이) 진행, 각자 자기 제시어로 시작
- 단계 순서:
  1. 모든 플레이어가 자기 시트의 제시어 작성
  2. 시트가 다음 사람에게 넘어감 → 그림 그리기
  3. 그 다음 사람 → 그림 보고 텍스트 답
  4. 반복 (총 N단계, 시작 제시어 작성자에게 돌아오면 종료)
- 타이머: 그리기 10~60초(기본 30), 텍스트 10~60초(기본 10), 5초 단위
- **점수 공식 제안 (체인 보너스)**:
  ```
  단계마다 다음 사람의 답이 이전 제시어와 "의미적으로 연결"되면 +점수
  ```
  - 자동 판정은 어려움 → **종료 후 시트 리뷰 단계에서 플레이어 투표** (각 단계마다 ⭕/❌)
  - 점수: 각 단계 ⭕ 받은 단계 작성자 +100점, 시트 전체가 ⭕면 시트 참여자 전원 +500 보너스
  - 추가 베스트 시트 투표(가장 웃긴 시트) → 시트 참여자 전원 +200
- 라운드 종료 후 쿠키 영상: 제시어 + 그리는 과정 배속 재생 → GIF 저장 (기술 스펙은 §11)

- 2~3위 좌우 배치

- 30초 후 자동 또는 '나가기' 버튼

## 10. 오프라인 / 예외 처리

- Socket.io `disconnect` 이벤트 → 30초 reconnect grace
  - 30초 내 복귀: 자리 유지
  - 초과: 자동 퇴장
- 게임 중 인원 < 3명 → 게임 자동 종료, 진행분만 결과 표시
- 출제자 이탈 (모드 1): 해당 라운드 무효 + 다음 사람으로 스킵
- 시트 담당자 이탈 (모드 2): 자동 "(빈 시트)" 처리 후 다음 단계로

## 11. 기술 스펙: 획 데이터 저장 / 동기화 / GIF 변환

### 11-1. 획 데이터 구조

```ts
type Stroke = {
  id: string;            // uuid
  authorId: string;
  color: string;         // '#000000'
  width: number;         // 픽셀
  points: Point[];       // 시간 정렬
  startTime: number;     // 라운드 시작 기준 ms
};

type Point = {
  x: number;             // 0~1 정규화 (캔버스 너비 비율)
  y: number;             // 0~1 정규화
  t: number;             // stroke 시작 기준 ms (재생용)
};
```

좌표 정규화 이유: 디바이스마다 캔버스 크기가 다름. 0~1로 저장해야 다른 화면에서도 동일 비율로 재현 가능.

### 11-2. 실시간 동기화

- **send 전략**: 점 단위 전송 X (트래픽 폭발) → **50ms throttle batch**로 묶어서 전송
- 이벤트 설계:
  - `stroke:start` { strokeId, color, width, startTime }
  - `stroke:append` { strokeId, points: Point[] }  ← 50ms마다
  - `stroke:end` { strokeId }
  - `stroke:undo` { strokeId }
  - `stroke:clear` (출제자만)
- **점 단순화**: Douglas-Peucker로 stroke 종료 시점에 30~50% 점 절감 후 서버 저장본 갱신
- **서버 권한**: 출제자가 아닌 사람이 보낸 stroke 이벤트는 거부 (치팅 방지)

### 11-3. 서버 저장

- **진행 중**: Redis Hash
  ```
  game:{roomId}:strokes  →  [stroke1, stroke2, ...]   (TTL 1시간)
  ```
- **종료 후 (모드 2 쿠키 영상용)**: PostgreSQL JSONB
  ```sql
  CREATE TABLE game_replays (
    id UUID PRIMARY KEY,
    room_id TEXT,
    sheet_index INT,
    step_index INT,
    prompt TEXT,
    strokes JSONB,
    created_at TIMESTAMPTZ DEFAULT now()
  );
  ```
- 영구 저장은 모드 2만 (모드 1은 라운드 끝나면 폐기 — 용량 절약)

### 11-4. GIF 변환 (모드 2 쿠키)

두 가지 옵션 비교:

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. 클라이언트 측 (Skia 프레임 캡처 + gif 인코딩) | 서버 부하 0 | 모바일 메모리/배터리 부담, 큰 GIF 어려움, 라이브러리 미성숙 |
| B. 서버 측 (stroke 데이터 → 프레임 렌더 → GIF) | 모바일 부담 0, 빠름, 안정적 | 서버 비용 증가, 구현 복잡 |

**권장: B (서버 측)**

서버 GIF 생성 파이프라인:

```
client                server
  │                     │
  │ POST /replays/:id/gif (요청)
  │────────────────────▶│
  │                     │ 1. PG에서 strokes 로드
  │                     │ 2. node-canvas로 빈 캔버스 생성
  │                     │ 3. 각 stroke의 point.t 시간 흐름대로
  │                     │    프레임 단위(20fps = 50ms마다) 렌더
  │                     │    → PNG 버퍼 배열
  │                     │ 4. gifenc로 GIF 인코딩 (배속 옵션 적용)
  │                     │ 5. S3(또는 Railway 볼륨)에 업로드
  │ 200 { url }         │
  │◀────────────────────│
```

- 라이브러리: `canvas`(node-canvas) + `gifenc`
- 프레임율: 20fps (모바일 친화), 배속 2~4배 → 5~10초 안에 재생 완료
- 색상: 256색 팔레트 양자화 (gifenc 자동)
- 파일 크기 목표: 1MB 이하 (canvas 800×800 기준)
- 다운로드: 클라이언트가 URL 받아서 `expo-file-system`으로 저장 → `expo-media-library`로 갤러리 저장

대안: `@shopify/react-native-skia`의 `makeImageFromView` + 프레임 캡처도 가능하지만, 위 이유로 비권장.

### 11-5. 그리기 재생 (시상식/리뷰용)

- 클라이언트도 동일 stroke 데이터로 Skia 위에서 재생 가능
- `requestAnimationFrame`으로 `point.t` 따라 진행
- 같은 데이터로 화면 재생 + 서버 GIF 둘 다 만들어지는 게 핵심 장점

## 12. 픽셀아트 캐릭터 제안

- 총 **20종** (동물 10 + 과일 10)
- 잠금 없이 처음부터 전부 선택 가능 (유료 모델 안 갈 거면 깔끔)

| 동물 | 과일 |
|---|---|
| 강아지, 고양이, 토끼, 곰, 여우 | 사과, 바나나, 딸기, 수박, 포도 |
| 펭귄, 햄스터, 너구리, 사자, 호랑이 | 오렌지, 키위, 파인애플, 복숭아, 레몬 |

스펙:
- 64×64 픽셀, PNG 8비트, 투명 배경
- 액자(frame)는 별도 9-slice PNG → 캐릭터 위에 합성
- 말풍선용 idle/talking 두 프레임 (선택사항)
